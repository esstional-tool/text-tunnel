# 바뀐 부분만 보내기: dirty rectangle 과 키 프레임 + 조각

> 이슈 [#24](https://github.com/esstional-tool/text-tunnel/issues/24) · 2026-10-20
> 1단계는 매번 화면 전체를 JPEG 한 장으로 보냈다(초당 5장 ≈ 150KB/s). 화면 대부분은 가만히 있으므로, **바뀐 곳만 보내면** 같은 화질로 전송량이 수십 배 줄어든다. 원격 화면 공유(VNC·RDP·화상회의 화면 공유)의 가장 기본적인 최적화다.

## 핵심 아이디어

```
에이전트: 지금 화면 ──(이전 화면과 칸 단위 비교)──▶ 바뀐 사각형들 ──▶ 조각(JPEG) 묶음 ──▶ 서버
서버:     키 프레임 1장 + 조각 목록(번호순)  ── "내가 마지막으로 받은 번호(since) 이후" ──▶ 보는 화면
보는 화면: 캔버스 위에 조각을 같은 좌표에 덧그림
```

## 새로 쓴 기술

### 1. 칸(tile) 단위 비교와 사각형 합치기

- **개념**: 화면을 64x64 칸으로 나눠 이전 화면과 **바이트로 비교**한다. 픽셀 하나하나가 아니라 "한 칸에 하나라도 다른 바이트가 있으면 바뀐 칸"으로 본다. 칸이 클수록 비교는 빠르고 보내는 영역은 커진다(트레이드오프).
- **이 코드에서는**: 이전 화면을 비관리 메모리(`Marshal.AllocHGlobal`)에 두고, 현재 화면 비트맵을 `LockBits` 로 잠가 칸의 각 줄을 `memcmp`(C 런타임)로 비교한다. 바뀐 칸이 가로로 이어지면 한 사각형으로, 위아래로 가로 범위가 같고 맞닿으면 세로로도 합친다(실제 시험: 세로로 긴 변화 → 128,0 크기 64x256 하나).
- **함정**: 비트맵의 한 줄은 `Stride`(4바이트 정렬된 줄 길이)이므로 `x*3` 이 아니라 `y*Stride + x*3` 으로 계산해야 한다. 가장자리 칸은 64보다 작다.
- **한계**: 칸이 아주 많이 바뀌면 조각을 여럿 보내는 것보다 전체 한 장이 싸다 → 면적 60% 이상이면 전체, 사각형이 12개를 넘으면 하나의 큰 사각형으로 묶는다.

### 2. 키 프레임 + 조각 (비디오 압축과 같은 구조)

- **개념**: 동영상의 I-프레임(독립)/P-프레임(이전에 의존)과 같다. 조각만 받아서는 그림이 안 되므로 **기준이 되는 전체 화면(키 프레임)** 이 반드시 필요하다.
- **언제 키 프레임을 보내나**: 처음 · 보는 사람이 없다가 생김 · 화면 크기 변화 · 바뀐 면적 큼 · 10초마다(오차 누적 방지) · **서버가 요청** · 전송 실패(조각을 잃었으니 기준을 다시 맞춤).
- **조각이 계속 쌓이는 문제**: 서버는 이미지를 풀지 못하므로(의존성 0) 조각을 **합칠 수 없다**. 대신 조각이 키 프레임 크기의 2배를 넘으면 응답으로 `key` 를 돌려 에이전트에게 새 전체 화면을 요청한다. 새 키 프레임이 오면 이전 키·조각은 전부 버린다 → 서버 메모리는 "키 1장 + 일정 한도의 조각"으로 유계(bounded). 안전 상한 6MB 를 넘으면 모두 버리고 기다린다.

### 3. "내가 마지막으로 받은 번호" 로 따라잡기 (pull + cursor)

- 기존의 "최신 한 장만 가져오기"는 조각 방식에서는 안 된다(중간 조각을 건너뛰면 그림이 깨진다). 대신 보는 쪽이 `since=마지막으로 그린 번호` 를 보내면 서버가 그 뒤 조각을 **번호순으로 묶어** 준다. 늦게 들어왔거나, 키 프레임보다 옛 번호면 키 프레임부터 준다. 새 것이 없으면 204.
- 가져오는 중에 알림이 여러 번 와도 끝난 뒤 한 번만 다시 가져온다(coalescing) — 중간을 건너뛰어도 한 묶음에 다 들어 있다.
- 묶음 형식은 직접 정한 이진 포맷(`TTF1` + 번호 + 화면 크기 + 개수 + {x,y,w,h,길이,이미지}) 이고 서버는 **길이 합이 정확히 맞는지, 화면 안인지, 이미지로 시작하는지**만 검사한다.

### 4. 브라우저에서 조각 덧그리기

- 각 조각을 `createImageBitmap(Blob)` 으로 디코딩(한꺼번에 병렬) → `drawImage(bitmap, x, y)` 를 **순서대로**. 디코딩은 병렬이어도 그리기 순서는 지켜야 같은 칸에 겹친 조각이 최신으로 남는다.
- 캔버스 크기를 바꾸면 내용이 지워지므로, 크기는 키 프레임(화면 크기가 바뀔 때는 항상 키)에서만 바뀐다.

### 5. 합성 화면으로 시험하기 (`--fake-screen`)

- 진짜 화면은 시계·커서·알림으로 늘 조금씩 바뀌고, 시험 중 사용자의 화면 내용을 읽게 된다. 에이전트에 `fake-screen.txt` 로 그리는 합성 화면 모드를 두어 **정확히 어느 칸이 바뀌는지** 정하고 그 칸만 오는지 확인했다. 브라우저 시험은 캔버스 픽셀 색(빨강·초록·바탕)을 읽어 조각이 올바른 자리에 덧그려졌는지 확인했다.

## 시험에서 배운 것

- **시험 가정이 깨졌다**: 예전 시험은 "3.5초에 18장 이상"을 요구했다. 바뀐 곳만 보내면 정적인 화면에서는 프레임이 거의 없는 것이 *정상*이다. 성능 개선은 기존 시험의 가정을 바꾼다 — 시험을 "프레임이 많다"에서 "첫 화면은 오고, 바뀔 때만 온다"로 고쳤다.
- 칸 경계: 30x30 변화가 칸 경계(128)를 넘으면 두 열이 바뀐다. 시험 좌표를 칸 안에 두어(70,70) 기대값을 명확히 했다 — 경계 효과 자체가 칸 크기의 비용이다.
- 속도 표시: 합성 애니메이션 기준 약 150KB/s → 약 6KB/s (조각 2개, 평균 1.5KB). 정지 화면은 0.
