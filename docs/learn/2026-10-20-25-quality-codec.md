# 화질·속도 자동 조절(backpressure)과 코덱 선택(JPEG/PNG)

> 이슈 [#25](https://github.com/esstional-tool/text-tunnel/issues/25) · 2026-10-20
> 조각 전송([노트](2026-10-20-24-dirty-rect.md)) 위에, "네트워크가 느릴 때 어떻게 버티는가"와 "같은 영역을 어떤 형식으로 인코딩하는가"를 더했다.

## 어떤 문제였나

- 화질 60·초당 5번은 빠른 회선에는 아깝고 느린 회선(Render 무료 서버, 모바일)에는 과하다. 고정값은 어느 쪽에도 맞지 않는다.
- JPEG 는 사진에 강하지만 글자·UI 같은 단순한 영역에서는 번지고 오히려 크다. PNG 는 반대다.

## 새로 쓴 기술

### 1. 피드백 제어: 측정 → 조절 (AIMD 비슷한 규칙)

- **개념**: 보내는 쪽이 "지금 내 보내기가 얼마나 걸리는지"를 재고, 막히면 빨리 줄이고(곱/큰 폭 감소) 여유가 있으면 천천히 늘린다(가산/작은 폭 증가). TCP 혼잡 제어(AIMD)와 같은 철학이다. 늘릴 때는 조심스럽게, 줄일 때는 과감하게 해야 진동하지 않는다.
- **이 코드에서는**: 올리는 요청의 응답 시간을 지수이동평균(EMA, 0.6·이전 + 0.4·새 값)으로 본다. `EMA > 700ms` 이거나 서버가 `slow` 라고 하면 **품질 −10, 간격 +80ms**, `EMA < 250ms` 이면 **품질 +4, 간격 −20ms**. 범위(프로필)가 상·하한을 정한다. 시험(지연 0.9초): 화질 85 → 45, 간격 150 → 470ms, 풀리자 85·210ms 로 복귀.
- **한계**: 업로드 응답 시간은 "에이전트 → 서버" 구간만 잰다. "서버 → 보는 사람" 구간은 모른다 → 아래 2번이 필요하다.

### 2. 보는 쪽이 못 따라오는 것을 서버가 알려 주기 (end-to-end backpressure)

- **개념**: 생산자(에이전트)–중계(서버)–소비자(보는 화면) 사슬에서 가장 느린 곳이 전체 속도를 정해야 한다. 소비자가 느린데 생산자가 계속 보내면 중계 메모리만 쌓인다.
- **이 코드에서는**: 서버는 보는 사람마다 "마지막으로 가져간 번호(`since`)"를 기억한다. 프레임을 올릴 때 **어떤 보는 사람이든 8개 넘게 못 받았거나, 새 것이 있는데 1.5초 넘게 안 가져갔으면** 응답에 `slow` 를 붙인다(`ok slow`). 에이전트는 이를 신호로 쓴다. 서버는 이미지를 이해하지 못해도 **번호만으로** 이 판단을 한다. (탭이 숨겨져 안 가져가는 사람도 자연스럽게 "느림"이 되어 전송이 줄어든다.)
- **주의**: 응답 문자열에 정보를 덧붙이는 방식은 간단하지만 하위 호환이 깨질 수 있다. 에이전트는 `Split(' ')[0]` 으로 판정과 표시를 분리해 읽는다.

### 3. 조각마다 JPEG vs PNG: 가장 작은 쪽을 보낸다

- **개념**: 손실 압축(JPEG)은 사진처럼 부드러운 변화에, 무손실 압축(PNG, 반복 패턴·같은 색 구간을 잘 줄임)은 단색·글자·선처럼 색이 적은 영역에 유리하다. 화면 공유는 둘이 섞여 있으므로 **영역별로 둘 다 인코딩해 작은 쪽**을 고르는 것이 가장 간단하고 효과적이다.
- **이 코드에서는**: 100만 픽셀 이하 영역만 PNG 도 시도(GDI+ PNG 인코딩이 느려서). 시험 결과: 단색 사각형은 PNG 283B, 잡음(사진 흉내)은 JPEG 11KB(같은 영역을 PNG 로 하면 수십 KB). 서버·브라우저는 형식을 몰라도 된다(`createImageBitmap` 이 파일 머리로 판별, 서버는 JPEG/PNG 머리 바이트만 확인).
- **부수 효과**: PNG 조각은 무손실이라 글자가 번지지 않는다 — 화질 낮춤(품질 25)과 상관없이 선명하다.

### 4. 프로필: 사용자의 선택은 "범위", 결정은 에이전트

- 보는 사람은 `자동 / 화질 우선 / 속도 우선` 만 고른다. 서버가 값을 검사(`Set` 에 있는 문자열만)하고 에이전트가 **자기가 정한 범위**(자동 30~85, 화질 70~92, 속도 25~50 + 가로 960px)로 해석한다. 공격자가 서버를 통해 임의의 값을 넣어도 에이전트 범위를 벗어나지 못한다. 크기가 바뀌므로 프로필 전환은 키 프레임부터 다시 보낸다.

### 5. 느린 네트워크를 시험에서 흉내 내기

- 진짜 느린 회선을 쓰지 않고, 에이전트와 서버 사이에 **지연 프록시**(Node `http` 로 `POST /frame` 만 0.9초 늦춤)를 끼웠다. 에이전트는 `--server` 만 바꾸면 되고, 프록시는 SSE 같은 다른 요청은 그대로 통과시킨다. 같은 방식으로 패킷 손실·대역폭 제한도 시험할 수 있다(다음 단계).

## 시험에서 배운 것

- 보는 쪽 시험은 "프레임을 제때 가져가는 보는 사람"을 흉내 내야 한다. 안 가져가면 서버가 `slow` 를 주어 에이전트가 화질을 내려 버리므로, 시험 결과가 "네트워크 지연" 때문인지 "시험용 보는 사람이 느려서"인지 섞인다.
- 화면 크기가 달라지는 프로필 전환(960↔1280)에서는 캔버스를 비우고 키 프레임이 다시 오므로, 픽셀 확인은 **전환이 끝나고 합성 화면이 가만히 있을 때** 해야 한다(애니메이션이 화면 내용을 덮어쓰는 시험 실수를 한 번 했다).

## 다음 공부 거리

- 대역폭 추정(패킷 쌍)·BBR 같은 최신 혼잡 제어, 프레임 우선순위(마우스 주변을 먼저)
- 영상 코덱(H.264/VP9)과 WebCodecs/WebRTC: 키 프레임·델타 프레임이 코덱 안으로 들어가고, 움직임 보상으로 스크롤·동영상에 훨씬 강하다
- 색 수 기반 자동 판별(히스토그램)로 PNG 시도 전에 가볍게 걸러내기
