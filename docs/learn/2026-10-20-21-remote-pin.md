# 접속 PIN: 조종당하는 PC 의 주인이 정하고, 그 PC 가 직접 확인한다

> 이슈 [#21](https://github.com/esstional-tool/text-tunnel/issues/21) · 2026-10-20
> 원격 화면 보기([노트](2026-10-20-17-remote-view.md), [알림](2026-10-20-19-agent-alerts.md))에 "승인 PIN"을 추가했다. 처음 설계는 PIN 을 서버/보는 쪽 어딘가에 두는 느낌이었는데, **PIN 은 화면을 내주는 쪽(에이전트 PC)의 주인이 정해야 한다**는 요구로 바꿨다.

## 어떤 문제였나

짝 열쇠(key)만으로 화면을 볼 수 있으면, 열쇠가 새는 순간(공유 PC, 어깨너머, 저장된 브라우저 데이터) 누구든 내 화면을 본다. 열쇠와 **별개의, 화면의 주인만 아는 두 번째 비밀**이 필요하다. 이 비밀을 서버가 알면 서버(=남의 컴퓨터)를 믿어야 하므로, **정하는 것도 확인하는 것도 에이전트 PC** 에서 한다.

## 설계 결정

| 질문 | 결정 | 이유 |
|---|---|---|
| 누가 PIN 을 정하나 | 에이전트 PC 의 주인 (트레이 메뉴 / `--set-pin`) | 화면을 내주는 사람이 문을 연다 |
| PIN 을 정하기 전 | **아무도 못 본다** (기본 거부) | "깜빡하고 안 정함"이 곧 노출이면 안 됨 |
| 어디에 저장 | 에이전트 옆 `pin.dat`, PBKDF2 해시만 | 파일이 새도 PIN 을 바로 알 수 없게 |
| 누가 맞는지 확인 | 에이전트 | 서버는 PIN 을 **중계만** 하고 저장·비교하지 않음 |
| 틀리면 | 5번 → 에이전트 10분 잠금 | 6자리 숫자는 100만 가지뿐 — 횟수 제한이 본체 |

## 새로 쓴 기술

### 1. PBKDF2 로 비밀번호 해시 저장

- **개념**: 비밀번호를 그대로 저장하지 않고, 소금(salt)과 함께 **일부러 느린** 해시를 여러 번 돌려 저장한다. 파일이 유출돼도 하나씩 대입해 보는 비용이 커진다.
- **이 코드에서는**: C# `Rfc2898DeriveBytes`(= PBKDF2-HMAC-SHA1), 반복 100,000회, 무작위 salt. 비교는 길이가 같은 바이트열을 끝까지 비교(조기 종료 없음).
- **주의할 점**: 6자리 숫자는 해시가 느려도 **오프라인으로 전부 대입 가능**하다(100만 번). 그래서 해시는 "파일 유출 시 시간 벌기"이고, 실제 방어는 **온라인 시도 횟수 제한(잠금)** 이다. 길게 정할수록 좋다(최대 12자리).

### 2. 검증을 맨 끝(에이전트)에서 하는 구조 (end-to-end 검증)

- **개념**: 중간(서버)은 믿지 않는 길(untrusted relay)로 취급하고, 비밀을 아는 양 끝에서만 판단한다.
- **이 코드에서는**: 보는 쪽 `POST /view/auth {pin}` → 서버가 SSE 로 에이전트에 `{type:'auth', vid, pin}` 전달 → 에이전트가 해시 비교 → `POST /agent/auth {vid, ok, left, locked}` → 서버가 그 보는 기기만 `ok=true` 로 표시 → 그때부터 프레임 GET 허용. 서버는 `ok` 가 아니면 프레임을 **403** 으로 막는다.
- **주의할 점**: 서버가 PIN 문자열을 중계하므로 서버를 완전히 신뢰하지 않는다면 PIN 을 서버가 못 보게(챌린지-응답, PAKE 등) 해야 한다. 이 앱은 개인용·서버 직접 운영이라 중계까지만 허용했다. 서버는 로그에도 PIN 을 남기지 않는다.

### 3. 이중 잠금 (에이전트 + 서버)

- 에이전트: 연속 5번 틀리면 10분 잠금(잠금 중에는 맞는 PIN 도 거절), 접속 기록(`access.log`)에 실패만 남김.
- 서버: 보는 기기(viewer)당 5번, 열쇠(key)당 10분에 10번. 에이전트가 꺼져 있거나 이미 확인 중이면 409, 한도 초과면 429. 확인 응답이 오지 않으면 8초(`REMOTE_AUTH_TIMEOUT_SEC`) 뒤 실패 처리.
- **왜 둘 다**: 서버 제한은 공격자가 새 연결을 계속 만드는 것을 막고, 에이전트 제한은 서버를 우회한 시도(재시작, 다른 서버 경로)에도 PC 가 스스로 지킨다.

### 4. 연결이 끊겼다 돌아올 때의 재인증

- 에이전트가 재시작되면 이전 인증은 무효(서버가 에이전트 연결이 끊긴 순간 모든 보는 기기를 `ok=false` 로). 보는 화면은 **방금 성공한 PIN 을 화면 메모리에만** 들고 있다가 한 번 자동 재전송한다. 새로고침하거나 뒤로 가면 사라지고 localStorage/sessionStorage 에는 쓰지 않는다(시험으로 확인).

## 시험에서 배운 것

- 서버 51항목(가짜 에이전트가 PIN 482915 를 확인), 에이전트 32항목(진짜 exe: 해시 저장·재시작 후에도 유지·잠금·로그에 PIN/열쇠 없음), 보는 화면 19항목(틀린 PIN 의 남은 횟수, 자동 재인증, 저장소 미저장).
- **빌드 실패가 옛 exe 를 남기는 함정**: 컴파일이 실패해도 이전 exe 가 남아 시험이 "통과"해 버렸다. `build-agent.cmd` 가 먼저 exe 를 지우고 `BUILD OK/FAILED` 를 출력하게 고쳤다.
- **시험 순서**: `pair.test.js` 의 마지막 항목이 IP 를 10분 차단한다. 에이전트 시험이 그 뒤에 돌면 429 로 실패하므로 pair 는 마지막에(또는 서버 재시작).
- 응답 JSON 에 서버의 `status:'checking'` 필드가 있어서 시험 도우미가 만든 HTTP `status` 를 덮어썼다 → HTTP 상태를 객체의 **마지막**에 두었다.

## 다음 공부 거리

- PIN 해시 파일을 DPAPI(`ProtectedData`)로 한 번 더 감싸기, 열쇠 파일도 마찬가지.
- 서버가 PIN 을 못 보게 하는 PAKE(SRP/OPAQUE) — 중계를 믿지 않는 인증.
- 일회용 코드(TOTP)와 접속 승인 팝업(주인이 직접 "허용" 클릭)의 비교.
